如果我们可以忽略现有网络设备和协议的限制，重新为容器设计一套网络，这套网络应该提供什么样的语义？

这个问题不是抽象的。Kubernetes 的网络模型并不是从现有的技术栈里挑选了几种协议拼凑而成，而是先确立了一组理想化的语义目标，再围绕这些目标演化出 Pod、Service、NetworkPolicy 等概念。理解这组理想语义，比先记住 CNI、VXLAN、iptables 等名词更重要。

## 理想之一：每个容器应该像一台独立主机

容器本质上是一组共享内核的进程。但在网络层面，调用方不应该关心这个细节。一个容器应该和一台虚拟机或物理机一样，拥有一个独立的 IP 地址，能够直接接收和发送数据包。

这意味着：

- 容器内部的应用可以监听它认为的"本机"端口，而不必担心与宿主机或其它容器冲突。
- 网络诊断工具如 `ping`、`traceroute`、`tcpdump` 在容器里看到的网络行为，应该与一台独立主机相似。
- 安全策略、审计日志、流量监控可以以单个容器为单位进行，而不是以宿主机为单位。

为了实现这个理想，Kubernetes 没有直接把容器作为网络的最小单位。因为同一个 Pod 内的多个容器通常需要共享同一个网络命名空间、同一个 IP 地址和同一组端口空间。于是 Kubernetes 引入了 **Pod**：Pod 是网络的最小单位，一个 Pod 拥有一个独立的 IP。

## 理想之二：任意两个容器应该可以不经过 NAT 直接通信

在传统的 Docker 默认网络模型中，容器通过宿主机的 docker0 网桥通信。跨主机的容器之间通常需要源地址转换（SNAT）或端口映射才能互相访问。这种模型在单机上工作良好，但在集群规模下会带来问题：

- 调用方看到的源 IP 是经过转换后的宿主机 IP，导致基于 IP 的身份识别、白名单、审计失效。
- 端口映射让容器应用无法使用它真正监听的端口，管理复杂。
- 网络路径不直观，排查问题时需要在宿主机和容器之间反复跳转。

理想的容器网络应该像数据中心里的物理机网络一样：任意两台主机之间只要知道对方 IP，就可以直接发送数据包，中间不需要地址转换。

Kubernetes 把这个理想直接写进了官方文档：

> 所有 Pod 都可以在不使用 NAT 的情况下与所有其它 Pod 通信。
> 所有节点都可以在不使用 NAT 的情况下与所有 Pod 通信。
> Pod 看到的自己的 IP 与其它 Pod 看到的它的 IP 相同。

这三条规则定义了 Kubernetes 的 **扁平网络模型**。后续所有的 CNI 插件、Overlay 隧道、BGP 路由方案，本质上都是在不同的底层网络条件下满足这三条规则。

## 理想之三：容器迁移后，访问它的方式不应该改变

容器的生命周期是短暂的。Pod 因为调度、缩容、滚动更新、节点故障等原因被销毁重建后，它的 IP 地址通常会改变。如果调用方直接记住 Pod IP，那么每次后端变化都需要同步更新调用配置。

理想的语义是：调用一个服务时，只需要知道一个稳定的标识，而不需要关心当前有哪些 Pod、它们运行在哪些节点上、IP 是什么。

为了实现这个理想，Kubernetes 引入了 **Service**。Service 提供一个稳定的虚拟 IP 和 DNS 名称，将流量负载均衡到一组后端 Pod。调用方只需要知道 Service 的地址，Kubernetes 负责维护后端 Pod 列表的变化。

## 理想之四：网络策略应该基于身份，而不是基于 IP

在传统网络中，防火墙规则通常写成：

```text
允许 10.0.1.0/24 访问 10.0.2.0/24 的 3306 端口
```

这种规则在容器环境里很快会失效。Pod 的 IP 是临时的，今天属于"前端"应用的 IP，明天可能被一个完全不同的应用使用。按 IP 写规则意味着每次调度变化都要更新防火墙。

理想的网络策略应该基于身份而不是地址。例如：

```text
允许带有标签 app=frontend 的 Pod 访问带有标签 app=database 的 Pod 的 3306 端口
```

Kubernetes 为了实现这个理想，引入了 **NetworkPolicy**。它允许用户按 Pod 标签和命名空间标签定义规则，由 CNI 插件在底层将这些标签映射为具体的 IP 集合，并在 Pod 变化时自动更新。

## 理想与现实的距离

这四个理想构成了 Kubernetes 网络的设计假设。但理想不等于实现。在真实的数据中心里，底层网络往往不能直接把 Pod IP 当作可路由地址，宿主机内核的转发路径也未必足够高效，外部流量进入集群还需要额外的路由和负载均衡机制。

因此，Kubernetes 在网络层采用了分层解耦的设计：

- **Pod 网络层**负责让每个 Pod 获得独立 IP 并实现 Pod 间互通。
- **Service 网络层**负责提供稳定的虚拟端点和负载均衡。
- **Ingress / Gateway API 层**负责把外部流量按规则引入集群。
- **NetworkPolicy 层**负责按身份实施访问控制。
- 在它们之上，还有服务网格、多集群网络、Egress 控制、高性能网络等扩展层次。

每一层都不是独立存在的，而是围绕上述四个理想分别解决不同维度的问题。
